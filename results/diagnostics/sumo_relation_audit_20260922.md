# SUMO relation audit for doctrine formalization — 22 September 2026

This is an AI-only development audit of 13 previously source-checked passages: seven from FM 2-0 (2023), chapter 1, and six from ATP 2-01.3 (2019), chapter 1. It compares the passages with SUMO relation definitions and the project's doctrine extension. It does **not** change benchmark labels, assert new gold formulas, or constitute SME review. The ATP packet has already been exposed to a model diagnostic, so these findings are post-hoc development observations; a later evaluation needs fresh passages.

Sources: [FM AI review](../../data/benchmarks/fm2-0/chapter1-2023-review/review-batch-01-ai.csv), [ATP AI review](../../data/benchmarks/atp2-01-3/chapter1-2019-review-v2/review-ai.csv), [doctrine extension](../../data/ontology/doctrine_domain.kif), and the locally pinned `data/sumo` checkout at commit `909a1ecd30949b864405206e18579ffc37318242`. The source PDFs and numbered paragraphs were previously verified in [the AI review report](ai_review_20260922.md). SUMO is maintained in the upstream [ontologyportal/sumo](https://github.com/ontologyportal/sumo) repository. Relation signatures below were read from `Merge.kif` or `Mid-level-ontology.kif` in that checkout and compared with the local extracted `sumo_relations.jsonl`.

**Extractor finding and follow-up:** At audit time, `src/sumo/loader.py` stored both `(domain REL N Type)` and `(domainSubclass REL N Type)` as the same JSON `signature[N] = Type`. The follow-up extractor change adds `signature_kinds` for each argument and range, retaining `instance` versus `subclass`. A local regeneration against the pinned SUMO checkout retained all 1,504 relation records and their existing fields while adding this metadata. The live compiler and grounding path do not yet enforce the new kinds, and the generated vocabulary files are ignored artifacts that need regeneration where used.

## Relevant SUMO semantics

| Relation | Argument kinds and types | What it asserts | Consequence here |
| --- | --- | --- | --- |
| `subclass` | Class, Class | Every instance of the first class is an instance of the second. | A team is not thereby a *kind of capability* merely because it contributes to one. |
| `partTypes` | Class below Object, Class below Object | Every instance of the first type is part of an instance of the second type. | This does not say every whole has such a part; its direction matters. |
| `typicallyContainsPart` | Class below Object, Class below Object | An instance of the second type *typically* contains an instance of the first. | It adds typicality that the sampled “consist of” sentences do not state. |
| `component` | Instance of CorpuscularObject, instance of CorpuscularObject | One concrete thing is a component of another concrete thing. | It is an instance relation, not a direct relation between class names. |
| `subProcess` | Instance of Process, instance of Process | One process occurrence is a temporal part of another. | Generic process categories cannot be passed as event instances. |
| `agent` | Instance of Process, instance of AutonomousAgent | An agent participates in a process occurrence. | Generic doctrine about what staffs do needs explicit event and quantifier scope. |
| `instrument` | Instance of Process, instance of Object | An object is used by an agent in a process occurrence and remains unchanged. | “Employing capabilities” does not identify a specific tool occurrence. |
| `causes` | Instance of Process, instance of Process | One process occurrence brings about another. | A product driving a requirement is not automatically process-to-process causation. |
| `capability` | Class below Process, instance of CaseRole, instance of Object | An object has the ability to play a role in processes of a type. | This is not a container or membership relation for a “capabilities consist of” list. |

## Passage mapping

“Candidate” names a relation worth checking, not an accepted translation. A “partial claim” would require a separately defined extraction task that permits a source-entailing fragment rather than an equivalent representation of the whole sentence.

| Source paragraph | Source claim, shortened | Candidate | Audit result |
| --- | --- | --- | --- |
| FM 1-67 | CI capabilities consist of CI teams and biometric equipment. | `subclass`, `partTypes`, `typicallyContainsPart` | **No safe full mapping.** The local ontology models `CICapability` as `Object`, `CITeam` as `MilitaryUnit`, and equipment as `Device`. These types make a class-level part relation plausible, but `subclass` confuses assets with kinds of capability; `partTypes` has the wrong entailment for “each capability contains”; and `typicallyContainsPart` imports typicality. Existing draft stays unresolved. |
| FM 1-73 | HUMINT capabilities consist of teams, cells, and equipment. | Same class-level part relations | **No safe full mapping.** The same ambiguity recurs with three categories. It is useful development evidence for a domain-specific composition policy, not a second independent positive. |
| FM 1-51 | Assess is part of the overall assessment continuing activity. | `subProcess` | **Unresolved.** `subProcess` relates process occurrences. “Assess” and “assessment continuing activity” are generic activities here, with no named event or approved class-level temporal-part reading. |
| FM 1-54 | The intelligence warfighting function executes the intelligence process by employing capabilities. | `agent`, `instrument` | **No safe full mapping.** It joins execution, means, and a generic function. Neither an event instance nor a specific instrument is identified. |
| FM 1-79 | Open-source intelligence is intelligence produced from public information and handled for a requirement. | `subclass`, `resource` | **No safe full mapping.** The origin, processing, timing, and purpose conditions define the concept. A bare genus or process-role relation would omit them. The local `OpenSourceIntelligence` class is already under `IntelligenceDiscipline`; that background placement must not be mistaken for a source-derived result. |
| FM 1-115 | Intelligence architecture compiles capabilities, repositories, organizations, and personnel. | `component`, `partTypes` | **No safe full mapping.** The heterogeneous list describes an architecture; `component` requires concrete corpuscular objects, while the sentence names categories and a necessary-for-execution condition. |
| FM 1-42 | Commander and staff must establish and support an architecture. | `agent` | **Reject as an ordinary fact.** “Must” is an obligation, not a claim that the architecture or an establishing event exists. |
| ATP 1-1 | IPB is the systematic process of analyzing specified mission variables to determine effects. | `subclass` | **Possible partial claim only.** “IPB is a process” is entailed at the level of the sentence, but IPB is absent from the closed class vocabulary, and the full definition has analysis, variable, and purpose conditions. Adding `(subclass IPB Process)` to background before evaluation would make an identical predicted target circular. |
| ATP 1-14 | The operational environment is a composite of conditions, circumstances, and influences. | `partTypes`, `component` | **No safe full mapping.** The parts are abstract/heterogeneous and their effects on capabilities and decisions are part of the definition. The local ontology's `OperationalEnvironment` → `Region` deserves a separate modeling review; this sentence does not establish that genus. |
| ATP 1-23 | With no threat force, products about terrain, weather, and civil factors may support planning. | `agent`, `causes` | **Reject as an ordinary fact.** Both the no-threat condition and “may be sufficient” scope are essential. |
| ATP 1-33 | External assets provide expertise as input to IPB. | `instrument`, `agent` | **No safe full mapping.** Categories of assets, expertise, and an IPB process role are described generically; the instance-level roles need event and participant variables. |
| ATP 1-42 | The Army executes information collection through operations and intelligence processes. | `agent`, `instrument`, `subProcess` | **No safe full mapping.** “Through” expresses means and/or process organization, not necessarily the narrower `instrument` or `subProcess` semantics. |
| ATP 1-44 | IPB products drive information collection requirements. | `causes` | **Reject.** Product and requirement are not process occurrences. The prior model's existential `some ?x is-a Collection` is also unsupported by this relationship claim. |

## Decision

Upstream SUMO helps us reject incorrect mappings and supplies typed relation candidates, but these 13 passages do not justify adding a generic `part-of` or `causes` CNL form yet. With the extractor now preserving the distinction between `domain` and `domainSubclass`, the next pipeline step is to consume that metadata in validation and training-data selection. The best first semantic design target is a **claim contract**: distinguish (a) a formula equivalent to the complete passage from (b) a smaller, source-entailed atomic claim with its exact supporting span and an explicit `partial` flag. The current whole-passage labels must remain unchanged. Under the new contract, ATP 1-1 could supply a development example of the narrower “IPB is a process” claim, provided the IPB class declaration is separated from the source-derived `subclass` assertion and the example is never used as fresh evaluation.

Next, review the modeling of `CICapability` and `HUMINTCapability` before choosing a composition relation. In particular, decide whether these terms denote abilities, collections of assets, or operational resources, then specify the intended quantifier and direction. Only after that decision should a matching CNL form, compiler rule, and source-grounding gate be built. Use a new, prospective source packet to test the resulting system. SUMO axioms can validate types and support reasoning, but they cannot independently certify what an Army passage says.
